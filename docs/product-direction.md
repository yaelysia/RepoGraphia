# 产品方向：让人以较低理解成本掌控 AI 编程

2026-10-22。本文记录用户明确的产品目标、下一阶段选择和工程建设顺序。**这是开发方向，未实现能力不能按现有功能宣传。** 当前可用能力以 README 和实际实现为准。

## 产品目标

RepoGraphia 要降低 vibe coding 的理解成本，让编程理解不深的人也能看懂项目、审阅开发过程和比较结果，保持对项目的掌控。源代码图和功能图是理解、定位及审阅的入口。

| 时点 | 人需要回答的问题 | 产品应提供的信息 |
| --- | --- | --- |
| 开发前 | 项目有哪些能力？准备改的功能在哪里？ | 当前源码事实、粗粒度功能总图、准确代码关联和未探索范围 |
| 开发中 | 本轮实际改了什么？与声明目标是否一致？ | 相对本轮起点的代码变化、关联功能、待复核依据，以及单独标明来源的目标/解释 |
| 开发后 | 结果与修改前有什么不同？哪些地方仍需检查？ | 固定前后版本、功能及代码差异、审阅决定、验证证据与未确认事项 |

设计成效看人能否回答这些问题，而不只看图的节点数量、动画或程序测试数量。

## 已确定的下一阶段选择

- 围绕功能继续探索，同时补齐连续使用需要的项目绑定、更新和保存。
- 底层代码图应跟随工作区现状。首版工程默认跟随已保存文件，界面明确展示采集范围；编辑器未保存内容的接入后续单独扩展。
- 上层功能图支持局部续分析和对已有内容的增量修订，保留人工决定及历史。
- 先形成全项目粗粒度功能总图，再按需要逐层深入。实际已索引/已探索范围与未覆盖区域必须可见。
- 初版由网页准备任务，交给用户现有 Agent 执行；后续再增加界面启动 Agent 和运行状态管理。

“全项目总图”是内容组织目标，不自动扩大当前 TS/JS、单个所选 tsconfig 的分析范围。未索引语言、引用项目和未探索区域应明确列出，不能把一个叶项目的结果称为全仓库已分析。

## 连续工作区与版本

建议以轻量本地运行层承载文件观察、更新调度和可靠保存，复用现有浏览器工作台。历史离线 HTML 继续作为可导出的固定报告。首版聚焦一个已绑定项目，不以桌面安装包、多用户或云同步为前置。

需要区分三类版本：

1. **当前代码版本**：最近成功分析、核对过输入的代码图及其时间/范围。
2. **本轮任务起点**：开始一轮开发时保存的实际工作区图和标注版本，包含当时已有未提交修改；Git HEAD 只作辅助元数据。起点从固定并核对过的当时输入生成，存在待处理变化时显示“正在建立起点”，不得悄悄使用滞后缓存图。
3. **正在审阅的版本**：用户当前打开的证据、提案及编辑草稿所绑定的版本。

后台生成新图时，审阅内容和草稿保持原版本，并显示有更新可切换。接受操作绑定实际看过的内容和依据，不能自动代表后来的代码已通过。项目重新打开后应恢复已保存的数据和未完成审阅；保存状态应以实际落盘结果为准。

功能映射的接受、代码改动的审阅结论、测试/运行验证结果是不同记录。接受功能与代码的关联，不表示已经认可本轮代码修改，也不表示测试通过；后续任务审阅不能直接借用现有 mapping.decision 充当代码验收。

工作区数据存放在被分析源码树之外。源代码图更新、标注保存和人工审阅分别有自己的操作边界；该运行层不执行目标仓库应用或构建脚本。

## 底层代码图跟随变化

文件监听只是更新线索。配合启动、恢复、手动刷新及适当的目录/内容核对，合并连续保存事件，串行调度分析并防止旧结果覆盖新结果。显示“检测到变化／分析中／已核对至某版本／更新失败”等真实状态，失败时保留上一份有效图。

当前 `loadProject` 新建 TypeScript Program，`analyze` 完整提取节点和关系；值来源分析还依赖全项目调用点和写入索引。修改一个文件可能改变未修改文件的候选关系。因此第一步准确称为 **自动触发的完整重建**，不能称为真正局部增量提取。

先统一一次分析的输入读取：源码、根配置、继承配置、类型及模块解析相关输入都要记录。每个路径固定本轮读取内容，发布前核对输入清单和内容是否又有变化；无法确认一致时继续排队更新，不把中途混合读取的结果称为最新。该核验不等同文件系统原子快照；持续编辑也不能让界面无限等待。

性能优化优先复用锁定 TypeScript 的 Program/Builder/AST 能力，测量后分步推进。编译缓存复用与图的局部提取是两件事；后者必须维护跨文件关系和值来源索引，并与完整重建对照。配置、类型环境或无法可靠收窄的变化应回退完整重建。复用缓存时仍要保留全部分析输入的摘要。

代码实体及关系 ID 目前属于单次快照，位置移动或关系生成顺序变化都会改变 ID。跨版本差异应依据可核验的锚点和关系内容，不能把 ID 变化直接当成真实代码变化，也不能凭同名自动重绑。改变提取或 ID 语义时按 AGENTS.md 升级分析修订号。

## 上层功能图的增量维护

应将 **功能内容版本、人工决定、当前引用状态** 分开。工作区变化不应直接抹掉整张功能图，也不应把旧人工确认自动赋给新含义。

- 精确比较后仍匹配的引用：保留原内容和决定的版本出处，标明核对到了哪个代码版本；这只说明记录的依据仍匹配。
- 关联代码、关系或相关分析输入变化：标出原因，生成需要复核的功能范围。
- 无法匹配的引用：保留旧证据，进入重新定位/分析队列，不跳转同名当前代码。
- 新增或修改但没有功能归属的代码：独立进入待探索清单；不能因没有旧映射就忽略，也不能自动编造新功能。
- 修改父功能、含义或关联的提案：以新待审版本展示，原人工决定和历史仍可追溯。

复用现有 `feature-migration.plan` 的比较规则，但不直接放宽旧 `assess` 或 `migration.apply`。旧协议和旧报告保持原有快照/迁移规则；新契约需要明确版本与兼容方式。

现有 Agent 通道只能追加。真正的增量修订需另建可审阅变更包，记录任务 ID、图版本、标注 revision/digest、允许修订的对象、变更操作及支持/限制依据。文本 `scope` 本身不是可执行范围约束。沿用现有精确引用校验、层级校验、不可自行接受和原子应用要求；取消关联等改变应进入历史，不破坏性删除旧记录。

外部 Agent 完成时，工作区和标注可能已经变化。首版继续严格检查版本；迟到提案保存为旧基线结果，可阅读和重新准备任务，不能直接覆盖当前版本或手改快照字符串通过检查。复杂的并行提案合并可后续另行设计。

## 粗粒度总图与任务交接

先探索项目入口、实际行为和代码依据，形成主要功能与一句说明，再逐步细化。可以分批完成全项目探索；保留本轮范围、已核对文件/内容版本、未探索区域和待确认问题。目录名可以帮助定位，不足以证明业务功能；每个提案仍需独立依据。

用户可从功能节点、待复核项或未归属代码发起任务。任务包固定图及标注基线，包含声明目标、范围、现有结论、变化理由和验收点，交给现有 Agent/Skill。返回后先展示本批新增、修订和撤销关联的差异，再由人决定应用和审阅。全量重读整个项目不应成为每次局部更新的默认动作。

代码事实、Agent 解释和人工判断分开呈现。文件观察只能证明任务期间发现了哪些变化，不能证明修改者身份、Agent 意图、正在执行的步骤或任务完成。没有来源的目标/解释显示未知；初版不把“暂停观察”做成“停止 Agent”。

## 分阶段交付

| 阶段 | 可审阅交付 | 验收重点 |
| --- | --- | --- |
| M1 持续工作区与任务基线 | 绑定单项目、自动重建当前代码图、可靠保存、记录本轮起点、查看代码变化 | 连续保存不倒退、扫描中编辑不冒充最新、失败保留旧图、重开恢复、已有未提交修改正确纳入起点、待处理变化不被滞后缓存漏进本轮差异 |
| M2 总图建设与功能增量 | 全项目粗图任务、按功能/变化准备外部 Agent 任务、局部引用核对、修订提案对比与审阅 | 无关局部改动不抹掉全图；新代码进入待探索；修改现有功能有明确差异；迟到提案不覆盖现状；人工决定可追溯 |
| M3 开发过程与结果审阅 | 在现有工作台串起目标、任务期间变化、功能差异和前后对比 | 用户能定位本轮改了哪些功能、与声明目标的偏离、已核验和仍未知的部分；进一步降低原始源码阅读负担 |

M1 即提供代码事实层面的开发中/开发后比较，M2/M3 补上功能语义与更完整的审阅体验。阶段结束形成可用切片，不能把只有监听器或任务说明复制按钮的阶段称为整条流程完成。

后续界面启动 Agent、停止/恢复执行和精确进度，复用上述任务/版本契约再接运行适配器；不作为第一版的实现前提。

## 设计与验证依据

现有实现入口：`src/project.ts`、`src/analyze.ts`、`src/value-origins.ts`、`src/feature-map.ts`、`src/feature-migration.ts`、`src/agent.ts` 和 `viewer/feature-map-view.js`。当前契约见 [架构](architecture.md)、[功能标注](feature-mapping.md)、[迁移](feature-migration.md)、[Agent CLI](agent-cli.md)。

复用接口参考：

- [TypeScript Compiler API 的 Watch/Builder](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API#writing-an-incremental-program-watcher)：锁定 5.9.3 中已核对相应接口存在；它们不自动提供 RepoGraphia 的语义增量正确性。
- [Node.js 22 文件监听限制](https://nodejs.org/docs/latest-v22.x/api/fs.html#caveats)：平台、文件替换及缺少文件名等情况需要核对机制。

后续增量实现必须与同输入完整重建比较候选/未知/截断、具体关系、证据位置/哈希及来源停止原因，不能仅比较数量。用真实编辑序列验收新增、删除、改名、导出/类型变化、跨文件调用/写入变化、配置变化、扫描中编辑、未保存审阅与迟到提案。只有通过实际验证的阶段才写成已交付能力。
