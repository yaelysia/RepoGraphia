# 本地试用 M1、M2、M3

这份流程把三部分串成一轮：**M1 跟随已保存代码更新地图 → M2 建立功能理解 → M3 固定开发目标、比较变化并留下审阅记录**。全部在持续工作区完成；旧离线 HTML 不具备持续更新能力。

## 1. 更新并打开持续工作区

准备 Git、Node.js 22 或更高版本。以下用 Windows PowerShell，先把示例路径换成自己的实际路径：

| 路径 | 示例 | 用途 |
| --- | --- | --- |
| RepoGraphia 工具目录 | `D:\code\RepoGraphia` | 拉取代码、构建和运行 CLI |
| 要理解的项目目录 | `D:\code\my-app` | 分析其中已保存的源码 |
| 工作区保存目录 | `D:\repographia-workspaces\my-app` | 保存代码版本、功能标注、任务和审阅历史；必须在被分析项目之外 |

在工具目录检查本地状态：

```powershell
Set-Location "D:\code\RepoGraphia"
git status --short
```

如果列出自己的未提交修改，先保留这些修改，再继续更新，不要直接清空。然后执行：

```powershell
git switch master
git pull --ff-only origin master
npm ci --ignore-scripts
npm run build
node --version
```

PowerShell 若提示不能加载 `npm.ps1`，在相同命令中将 `npm` 换成 `npm.cmd` 即可。

启动工作区：

```powershell
node .\dist\cli.js workspace "D:\code\my-app" --out "D:\repographia-workspaces\my-app"
```

打开终端打印的**完整本机网址**，保留末尾的 `#token=...`，终端保持运行。顶部显示「已核对当前代码」后，先在「地图工作台」浏览目录、文件、函数和源码。

**已经用过 M1/M2，就继续使用原来的项目路径、`--out` 和 `--project` 选择。** M3 能恢复已有工作区，无需新建或重新导入初始标注。新工作区的输出目录可尚不存在或为空；普通离线报告目录不能直接当工作区。Monorepo 如需选一个子项目，可加 `--project "packages/app/tsconfig.json"`，实际覆盖范围以所选配置为准。

## 2. M2：先为项目建立一小张功能图

已有可用功能图时，可直接进入第 3 节。首次使用按下面操作：

1. 打开 **「功能建设」→「准备分析任务」→「建立项目粗图」**。
2. 在「本次希望弄清什么？」里写清目标，例如：“先解释少量主要功能，每个功能给出名称、一句解释和源码依据。对复杂功能，只在有依据时拆出子功能，保留不清楚的部分。”
3. 点击 **「生成固定任务包」→「下载任务包」**。
4. 把下载的 JSON 交给现有 Codex。下面的文字可以复制，路径要换成自己的绝对路径，任务文件名用实际下载名称。

```text
读取 D:/code/RepoGraphia/skills/repographia-function-map/SKILL.md，
按其中的任务修订流程执行。

CLI：D:/code/RepoGraphia/dist/cli.js
任务包：D:/repographia-trials/repographia-task-实际文件名.json
试跑记录目录：D:/repographia-trials/m2-notes-01
提交输出目录：D:/repographia-trials/m2-result-01（必须尚不存在）

先执行 agent task overview，再查询源码和关系证据。
按任务目标先解释一个小范围，提出 1–3 个有依据的主要功能，
给出名称、一句解释、支持依据、限制条件和尚未探索部分。
必要时明确提出子功能，不根据目录名或共享代码猜功能关系。
先写本层要回答的问题，保持同层功能的粒度可比较，并说明拆分理由。
保存起草前 claim table、自评、查询记录和 TRIAL.md。
使用任务包的冻结 header，不修改任务包或扩大允许范围。
不运行或修改目标项目，不代替我应用提案或接受关联。
check 通过后 submit，把 revision.json、review.json、receipt.json 的位置告诉我。
```

当前随附 Skill 1.4 会使用 `agent task overview/search/inspect/relation/check/submit`，并按 `references/construction.md` 检查本层问题、同层粒度与拆分理由。笔记目录和提交输出目录分开；`submit --out` 的目录到提交前必须尚不存在。准备任务包到应用这批提案期间，首轮试用可先暂停代码和标注编辑，便于完整走通流程。

Codex 返回后：

1. 在「功能建设」点 **「导入分析结果」**，选择返回目录中的 **`revision.json`**，确认来源名称，再点 **「保存并查看提案」**。
2. 在「按功能阅读」中核对名称、一句解释和该功能的各项变化，再查看相邻的支持／限制、完整说明与源码依据。本批未探索事项单独保留，不自动归入所选功能。
3. 填写「审阅者」和「本次决定的理由」，点击 **「应用本批修订」**。不认同整批结果时可选「拒绝本批提案」。
4. 回到 **「地图工作台」→「功能映射」**。应能看到名称和一句解释；有明确子功能的节点可以继续进入。需要更细时，再准备 **「深入一个功能」** 任务，选择对应功能，重复上述流程。

导入只保存提案，应用后才改变功能图。新增或改变的关联仍保持待审，可继续在地图中逐条判断。当前工作区流程导入的是 **`revision.json`**，不要混用旧离线流程的 `proposal.json` 或派生 `features.json`。

## 3. M3：固定目标，再观察一轮真实变化

建议在自己的试验分支或项目副本上选择一个小改动；本流程不要求运行目标应用。

1. 等代码核对完成、需要保留的标注已保存，点击 **「开始一轮开发」**。
2. 填写具体标题，展开 **「补充目标、功能范围与验收点（可选）」**，写目标说明，勾选明确关注的功能，每行写一个验收点。
3. 点击 **「建立起点」**。当时已保存的未提交修改也会纳入起点，后续比较只从这个实际状态开始。
4. 在编辑器中完成一个小改动并保存。例如，调整已关联功能中的一处实际实现；也可在所选 tsconfig 纳入的目录中新建一个简单 TS/JS 函数文件，观察未归属代码。不要只修改未保存的缓冲区或索引范围外的文件。
5. 回到工作区，等更新提示，点击 **「查看新代码版本」**。需要主动核对时点顶栏 **「检查更新」**。

现在用同一处改动查看三部分：

| 页面 | 应观察什么 |
| --- | --- |
| **M1：「代码变化」** | 起点与新版本的变化文件、源码差异；原阅读版本在主动切换前保持不变 |
| **M2：「功能建设」** | 受影响的原依据进入待复核，新文件或没有明确归属的代码进入待探索范围 |
| **M3：「开发审阅」** | 声明目标、相关功能记录、原标注涉及的变化文件、未归属项，以及本轮新增的待复核依据 |

**保存代码不会自动改写功能解释。** 底层代码图自动核对并完整重建；上层功能含义通过受审阅的提案更新。因此，“功能描述未变化”可以与源码变化、引用待复核同时出现。

开发审阅左边的 **「目标」「功能」「未归属」「记录」** 分别帮助定位验收点、功能变化、尚未解释清楚的代码和已保存结论。点功能详情中的「查看固定代码差异」，可继续看同一对版本的源码；「查看起点功能」和「查看审阅版功能」可回到对应地图。

## 4. M2：按变化继续修订功能图

在当前版本打开 **「功能建设」→「准备分析任务」→「按变化续分析」**。生成并下载新的任务包，让 Codex 按第 2 节的流程检查受影响的依据和新增代码，使用新的笔记／提交目录。返回后仍导入 `revision.json`，阅读差异，再决定是否「应用本批修订」。

应用后回到「开发审阅」，查看实际发生的功能说明、关联或审阅决定变化。功能语义更新也会形成新的比较版本。

如果任务返回时代码或标注已经变化，旧结果仍可阅读，但不能直接应用。点击 **「按当前版本重新准备」** 或重新准备分析任务；不要手改任务 header、版本或快照 ID 来绕过核对。

## 5. M3：保存结论、回看历史并重开

在「开发审阅」选一个功能或验收点，在右侧「留下这次审阅的结论」中选择记录类型：

| 记录类型 | 试用方式 |
| --- | --- |
| 人工代码审阅 | 填记录者，选择已审阅／需要修改／留待审阅，并说明理由 |
| 外部验证结果 | 填来源、方法和真实结果；尚未验证就选「尚未执行」，已有运行或测试证据再记录对应结果 |
| 补充解释 | 写清来源和仍需说明的情况 |

点击 **「保存这条记录」**，等成功提示，再点 **「导出这次审阅」** 保存这一份比较及已保存记录的 JSON。旧功能关联的「已接受」不会自动变成本轮代码通过审阅，也不会变成测试通过。

再保存一次代码修改，切换新版本后重新打开开发审阅：**新比较不会继承旧结论**。在左边「记录」中仍能打开前一份固定比较及其记录，历史保持只读。

最后在终端按 `Ctrl+C`，重新执行第 1 节相同的 `workspace` 命令，打开新输出的完整网址。代码版本、开发起点、已应用标注、分析提案和已保存的审阅历史应恢复。网页表单中尚未保存的文字不属于这些持久化记录；关页前先保存，或使用「导出未保存记录」。

## 7. 核对工作区和离线报告一致

在工作区选择要检查的代码与标注版本，等待标注保存完成，记下“功能建设”中的引用核对结果，再点击 **「导出报告」**。关闭工作区服务后打开新下载的 HTML，进入“功能映射”：

- “标注与文件”中应显示 **「导出版本引用核对」**，匹配及需复核数量与导出前所选版本一致。
- 打开一个匹配关联，代码节点与说明区应显示依据匹配；“查看核对后的代码依据”可在离线报告内打开该版本源码。
- 确实变化、无法定位或缺少原依据的条目仍分别显示需要复核、未匹配或尚未核实。
- 原有待审、接受或拒绝决定保持不变。引用匹配不代表功能含义、异步行为或外部行为已经得到验证。

若旧版本导出的 HTML 把全部依据显示成“失效”，更新并构建工具，重开**原工作区目录**，重新下载报告即可，不需要重跑 Agent 或重建功能提案。原 HTML 不会自动更新。仅用 `features render` 重新渲染 graph/features 不带工作区历史核对，仍采用严格快照规则。

离线核对结果固定于原导出版本。修改、成功导入或迁移标注后，页面会撤销旧核对结果并提示；失败的导入保留原文档和核对结果。需要新的核对结果时回到工作区重新导出。

## 已有离线报告怎么处理

旧 `graph.json` 与原先配对的 `features.json` 仍可离线阅读、重新渲染，继续浏览不需要重跑 Agent。新分析加入了输入身份核对，**源码没变也不保证旧图与新工作区的快照相同**，不能直接把旧标注强套为新工作区的 `--features`。

保留旧配对数据；需要带到新图时，先按 [显式迁移流程](feature-migration.md) 处理，或在新工作区通过固定任务建立功能图。已有 M1/M2 工作区则直接重开原目录。工作区内部的 `snapshots/<id>.json` 有额外封装，不要当普通 `graph.json` 交给 Agent；使用页面下载的任务包。
