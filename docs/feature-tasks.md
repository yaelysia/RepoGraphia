# 功能建设与增量修订（M2）

持续工作区中的 **「功能建设」** 将功能图建设拆成可审阅的小批次：准备固定任务包，交给现有 Codex/Agent 阅读，导入返回提案，逐项比较后整批应用。原有功能图继续承载名称、一句说明、显式子功能和代码依据；任务页面负责范围、待办和差异审阅。

## 1. 先建立粗图，再按需要深入

打开工作区并切换到当前代码与已保存的标注，在「功能建设」选择任务：

| 任务 | 用途 | 实际范围 |
| --- | --- | --- |
| 项目粗图 | 分批建立主要功能和一句解释 | 当前图的全部已索引文件、已有功能和关联 |
| 围绕功能深入 | 修订选定功能或继续拆解子功能 | 该功能的显式子树，以及任务包列出的代码文件和关联 |
| 按变化续分析 | 处理待复核依据和新增、未归属代码 | 当前引用待办、未归属代码和没有当前探索记录的文件，及其涉及的已有功能 |

任务包会明确列出允许改动的文件、功能、关联和父功能；自然语言目标不会扩大这些权限。功能任务的代码范围包含其映射和证据文件，以及直接静态关系涉及的索引文件。所选子树没有当前可用的依据文件时（包括原文件已退出索引），需要在全部已索引文件中寻找，任务包会明确列出这一范围。关系只帮助限定可探索的代码，不证明功能依赖。

子功能可继续准备任务，再向内拆分，没有“只能点开一层”的限制。功能层级由提案明确提供的 `parentId` 决定；父功能、文件映射和调用关系不会自动让子实体获得功能归属。文档仍有 1,000 个功能等容量预算。

构造时先明确这一层要回答的问题：总览说明主要能力，深入时解释组成、条件和边界。同层保持相近的解释粒度；拆分理由写入现有修订操作的 `reason`，不能为了画面整齐按目录、函数数量或固定层数生成子功能。每个父／子功能仍需自己的支持与限制依据。暂无子功能不表示分析已经完成，未探索事项也不会自动变成树上的占位功能。

“项目粗图”覆盖的是当前实际索引，不保证全仓库已分析。当前分析器以所选 tsconfig 的 TS/JS 为范围，未索引语言、引用项目、配置限制和未探索文件仍在范围说明中保留。

## 2. 把任务交给现有 Codex

准备后下载固定任务包。可以重复下载同一任务；它仍绑定准备时的代码和标注，不会变成后来的当前版本。任务包包含已索引源码，分享时应按源码文件处理。

向 Codex 提供以下内容，并将路径替换为本机绝对路径：

```text
读取 <RepoGraphia>/skills/repographia-function-map/SKILL.md，按任务修订流程执行。
CLI：<RepoGraphia>/dist/cli.js
任务包：<下载位置>/repographia-task-<id>.json
输出目录：<输出位置>/task-result-01（必须尚不存在）

先读 agent task overview，再查询源码和关系证据，按任务目标提出有依据的小批修订。
保留条件、候选、未知和未探索部分，记录起草前 claim table 与自评。
使用冻结 header，不改变任务包或扩大允许范围，不运行或修改目标项目。
check 通过后 submit；把 revision.json 和尚未核实的部分交给我审阅。
```

在 RepoGraphia 目录中，Agent 使用：

```sh
node dist/cli.js agent task overview "./task-bundle.json"
node dist/cli.js agent task search "./task-bundle.json" "入口关键词"
node dist/cli.js agent task inspect "./task-bundle.json" "<exact-node-id>"
node dist/cli.js agent task relation "./task-bundle.json" "<exact-relation-id>"
node dist/cli.js agent task check "./task-bundle.json" "./revision.json" --author "Codex"
node dist/cli.js agent task submit "./task-bundle.json" "./revision.json" --author "Codex" --out "./task-result-01"
```

查询可以分页；每个列表使用自己的 `nextOffset`。查询可查看任务包中的上下文，允许修改的范围由 `allowed` 单独控制。程序不运行模型，不启动目标应用、构建或测试；下载、返回提案和源码变化都不表示 Agent 执行进度。

`submit` 只写入 `revision.json`、`review.json` 和最后写入的 `receipt.json`。有效 receipt 表示结构、范围和引用检查通过，且 `applied: false`；它不证明语义正确，也不接受任何映射。输出路径拒绝覆盖。

Skill **1.4** 增加本层问题、同层粒度和拆分理由的构造指引与正反例，同时保留原离线 `agent overview/search/...` 追加流程；两种协议不要混用。工作区导入新流程的 **`revision.json`**，原离线流程仍产出 `proposal.json` 和派生 `features.json`。协议版本没有改变，声明表和自评仍保存在试跑记录中，不是新增的提案字段。

## 3. 阅读差异，再整批应用

在「功能建设」导入 `revision.json`，填写提案作者。作者是自述来源，不是身份认证。导入只保存提案，不改功能图，也不销毁地图中的草稿。

右侧先按功能选择本批内容，再逐项比较该功能的变化；功能名称与原说明来自固定任务或本批提议内容，不使用后来改名的当前功能冒充原版本。逐项保留：

- 新增或修订的功能名称、一句说明、详细解释和父功能。
- 新增或替换的关联，及其代码锚点、角色和理由。
- 撤销关联的理由；停用后保留原记录、证据和历史。
- 功能含义改变时，哪些已接受关联会回到待审。
- 精确源码中的支持与限制引文，以及 Agent 声明探索的文件和未探索部分。

支持与限制说明与当前选中的功能并置，精确引文和源码定位按需展开；较多检查保留“其余依据”入口。检查只属于本批提案及其固定代码版本，不是当前功能常驻的证明，也不意味着本批已经应用。仅撤销关联时显示撤销理由与原记录，不编造新的检查。没有内容操作的纯探索提案仍可完整阅读。

本功能的待确认问题与整批未探索事项分别展示，后者没有自动归入当前功能。新旧内容、原始变更记录和固定原始提案均保留，功能分组只改变阅读顺序，不改变整批决定的范围。

填写本次人工决定的名字与理由，选择整批应用或拒绝。应用将本批提案决定与新标注版本一次性保存；没有逐条偷偷部分应用。新增和改变的关联保持 `proposed`，之后仍可在功能图中逐条审阅。原内容、原人工决定和原依据版本可追溯。

“撤销关联”是应用后的关联停用；“拒绝本批”只给这份提案记录拒绝决定，不改变功能图。两者不同。

准备任务和应用提案前，页面会保护尚未应用的表单，并等待当前标注保存确认。提交期间暂时锁定地图编辑。导入、阅读或拒绝提案可以保留原地图和草稿。

## 4. 代码变化后看什么

原内容和人工决定保持原版本出处。持续工作区额外计算只读引用状态：

| 当前引用状态 | 含义 |
| --- | --- |
| 仍匹配 `matched` | 原精确锚点与静态邻域在当前版本仍对应；可打开核对后的当前代码 |
| 需要复核 `needs-review` | 源文件、相关静态关系、配置或类型环境等发生变化 |
| 无法定位 `unmatched` | 原实体无法在当前索引中精确定位；保留旧依据 |
| 未能核对 `unverified` | 缺少原图、输入记录或可验证依据；不推测当前对应实体 |

每条关联使用自己的原始 basis，混合多个旧版本的文档不会被统一冒充当前依据。完整比较保留候选、未知、类型关系、来源路径及预算停止；快照内 ID 变化本身不等于代码变化。源码位置移动或同文件哈希变化会要求复核，首版不做模糊重新绑定。

“仍匹配”只核对已有引用，不确认功能含义或本轮代码已验收；旧 `accepted` 也不代表后来的修改通过测试。原离线 `assess` 和显式迁移继续采用自己的严格规则，不因工作区的派生状态而放宽。

工作区的“导出报告”会把所选代码与标注版本的核对结果一起冻结到离线 HTML。名称、计数、代码节点和依据详情采用同一份结果；原关系 ID 不会被误当成新版本关系，调用箭头仍遵守原标注的严格快照规则。离线编辑、成功导入或迁移后撤销冻结结果；需要重新核对时从工作区重新导出。普通 `features render` 不读取工作区历史，仍显示严格快照评估。

未归属代码独立进入待探索清单，包括没有旧功能关联的新代码。被拒绝的映射不算当前归属；父功能或文件映射不会隐藏所有子实体。

## 5. 探索记录与迟到结果

探索记录来自**已应用提案**的 `exploredFiles`，绑定任务中的文件哈希。它表示“这批 Agent 声明读过此文件版本”，不证明完整理解。文件改变后显示记录已过期，没有记录的文件继续显示待探索。索引数量、声明探索数量和功能归属数量分别呈现，不合成为“全项目理解完成率”。

任务返回时，当前代码或标注可能已经改变。程序仍可验证并保存其原基线结果，供阅读、下载和拒绝；应用前会重新核对任务、代码快照、标注 digest/revision 及本机输入。只要基线不符，结果就保持只读，不能覆盖现状。可以按当前版本重新准备任务，不要修改旧 header 或快照字符串强行通过。

工作区关闭后重新打开，会恢复任务包、提案、人工决定和已保存的标注版本。尚未应用的浏览器表单仍需先处理；它不是已经落盘的提案或版本。

## 协议与存储

`bundleVersion: 1` 封装固定的 `taskVersion: 1`、图、标注和任务摘要；新修订使用独立的 `revisionProtocol: 1`。六个 header 字段是 `revisionProtocol`、`taskId`、`taskDigest`、`snapshot`、`baseDigest`、`expectedRevision`。

每批最多 20 个功能变更、100 个关联变更、100 个撤销、200 条引文、1,000 个声明探索文件和 100 项未探索说明；JSON 至多 5 MiB。详细字段、check/submit 命令和正反例见仓库 Skill 的 [task-revisions.md](../skills/repographia-function-map/references/task-revisions.md)。

任务和提案存放在源码树之外的工作区内，以内容摘要固定，manifest 保存其版本与决定。应用采用现有工作区的单写入者、不可变版本和原子 manifest 发布；磁盘失败不会把半批内容或未保存结果标成成功。任务包和 Skill 是协作约束，不能限制 Agent 在其宿主中已有的任意命令或文件权限。
